# Aggregate Feature Design (Shelved)

## Problem Statement
The current GraphQL API exposes list queries and relation connections with `PageInfo.TotalCount`, but dashboard/TUI use-cases need cheap aggregate values without fetching full edge/node payloads.

Current gaps:
- Counting related entities often requires querying full connection objects or multiple separate queries.
- Sum-style metrics (for example `SizeBytes`) are not available as first-class GraphQL fields.
- TUI/dashboard code ends up doing extra work (or SQL fallbacks) for simple aggregate needs.

Goal:
- Add a macro-driven aggregate API that is consistent with the generated GraphQL model.
- Keep reads on GraphQL query paths (except explicit DB panel exception).
- Preserve service-manager architecture and avoid reintroducing legacy side channels.

## Industry Patterns
Common patterns seen in production GraphQL APIs:

1. Connection + `totalCount`
- Relay-friendly baseline.
- Good for pagination count, weak for sums/avg/min/max.

2. Entity-specific aggregate fields
- Example: `MoviesAggregate(where: ...) { Count Sum { SizeBytes } }`
- Common in Hasura/PostGraphile-style schemas.
- Strong type safety and discoverability.

3. Top-level count/sum fields
- Example: `MoviesCount(where: ...)`, `MoviesSum(where: ...)`.
- Simple resolvers, very ergonomic for dashboards.

4. Generic aggregate container (your sketch)
- Example: `Aggregate { Count { Movies(...) } Sum { SizeBytes } }`.
- Flexible, but often less explicit and harder to keep strongly typed.

## Candidate API Shapes

### Option A: Entity-specific aggregate field (Recommended)
Pros: explicit, typed, composable, easy to document.

```graphql
query LibraryAggregateCounts($id: String!) {
  Library(Id: $id) {
    Id
    Name
    MoviesAggregate {
      Count
      Sum {
        SizeBytes
      }
    }
    MissingMovies: MoviesAggregate(Where: { HasFile: { Eq: false } }) {
      Count
    }
    ShowsAggregate { Count }
    AlbumsAggregate { Count }
    AudiobooksAggregate { Count }
  }
}
```

### Option B: Top-level aggregate fields
Pros: easiest to implement first; minimal schema complexity.

```graphql
query LibraryTopLevelAggregates($libraryId: String!) {
  MoviesCount(Where: { LibraryId: { Eq: $libraryId } })
  MoviesSum(Where: { LibraryId: { Eq: $libraryId } }) {
    SizeBytes
  }
}
```

### Option C: Generic `Aggregate` object
Pros: single conceptual entry point.
Cons: more custom schema machinery; weaker type discoverability.

```graphql
query LibraryAggregateCounts($id: String!) {
  Library(Id: $id) {
    Id
    Name
  }
  Aggregate {
    Count {
      Movies(Where: { HasFile: { Eq: false } })
    }
    Sum {
      SizeBytes
    }
  }
}
```

## Integration with Current Macro Stack
Relevant existing macro behavior:
- `GraphQLOperations` already generates list queries and uses `EntityQuery::count(...)` internally.
- `GraphQLRelations` already handles relation filtering/sorting/pagination and computes `total_count` for `PageInfo`.
- ORM already supports SQL builder patterns and typed where/order inputs.

### Implementation Direction
1. Add macro-generated aggregate types per entity:
- `<Entity>Aggregate`
- `<Entity>SumFields` (and optionally Avg/Min/Max later)

2. Add macro-generated aggregate query fields:
- Top-level: `<Entities>Aggregate(Where: ..., GroupBy?: ...)`
- Relation-level: `<RelationName>Aggregate(Where: ...)`

3. Reuse existing typed filter inputs:
- Same `<Entity>WhereInput` generated by `GraphQLEntity`.

4. Resolver strategy:
- Build SQL from existing filter pipeline.
- For aggregate fields, issue `SELECT COUNT(*), SUM(field)...` queries.
- Do not fetch edges/nodes when aggregate-only fields are requested.

5. Auth model:
- Keep the same `ctx.auth_user()?` checks as generated list queries.

## Suggested Rollout Plan
Phase 1:
- Add `Count` only (`<Entity>Aggregate { Count }`) for top-level and relation-level.
- Move TUI/library counts to aggregate endpoints.

Phase 2:
- Add `Sum` for numeric fields explicitly annotated as aggregatable.
- Candidate annotation: `#[aggregatable(sum)]` on entity fields.

Phase 3:
- Optional `Avg`, `Min`, `Max`, and maybe `GroupBy` if needed.

## Schema Design Notes
- Keep naming explicit (`MoviesAggregate`) rather than a single global `Aggregate` root.
- Ensure nullability semantics are clear:
  - `Count` should be non-null integer.
  - `Sum` fields can be nullable if no rows match.
- Preserve backward compatibility by adding fields, not replacing list APIs.

## Performance Considerations
- Aggregate resolvers should avoid loading rows.
- Prefer one SQL statement for all requested aggregate metrics per field group.
- Consider query complexity costs if many nested aggregates are requested.

## Risks / Open Questions
- How to expose `sum` only on numeric fields in generated schema cleanly.
- Whether relation aggregate fields should accept `OrderBy/Page` (likely no; only `Where`).
- Multi-tenant/user scoping: ensure aggregate queries enforce the same auth boundaries as list queries.

## Non-Goals (for now)
- Full OLAP/group-by cube APIs.
- Replacing all existing connection-based queries.
- Non-SQL data source aggregation.

## Recommendation
When resumed, start with **Option A (entity-specific aggregate field)** and implement **Count first**. It aligns best with current macros, keeps schema types clear, and addresses immediate dashboard/TUI needs with minimal risk.
