## Scope and caveat

This audit covers the current working tree, not only the last committed revision. The tree contains a
large, ongoing backend/GraphQL/frontend refactor, so findings were checked against the code that would
actually run today. The review included:

- repository rules and `docs/design.md`;
- scanner, matching, organization, metadata, authentication, artwork, casting, logging, and data-access
  paths;
- a read-only inspection of the active SQLite database and the current Movies library;
- targeted static searches for raw SQL, unfinished paths, panic sites, discarded errors, and unbounded
  network calls;
- comparison with the earlier `docs/audit-2026-07.md` and its progress documents.

This was not a penetration test. `cargo-audit` was not installed during the initial audit. The
remediation added CI advisory, license, unused-dependency, secret, production npm audit, and SBOM gates;
the Rust advisory tools still require CI or a workstation with those commands installed.

## Executive summary

The project has improved substantially since the 2026-07-02 audit. Mandatory JWT configuration, CORS
allowlisting, authenticated media routes, production GraphQL limits, SQLite WAL/busy-timeout settings,
graceful shutdown, completion reconciliation, atomic no-clobber file placement, manual-match protection,
auto-download, quality profiles, Torznab, HLS, and backup/object-storage work now exist in the current
tree.

The immediate Movies incident is a configuration block, not a filesystem-discovery failure: the active
Movies library contains eight discovered `MediaFile` rows but no `Movie` rows, and
`metadata.tmdb_api_key` is unset. With no existing movies to match locally, provider fallback is required;
every TMDB search failed with `TMDB API key not configured`, after which the scan still emitted a generic
INFO-level completion line. That explains both symptoms: no movies were added, and the user received no
clear actionable outcome.

The highest remaining risks are:

1. artwork fetching is still an SSRF-capable, no-timeout server-side URL fetch;
2. casting persists and exposes a user's real access-token-bearing stream URL in an unowned shared
   `CastSession`;
3. refresh tokens are still returned to JavaScript in GraphQL responses despite also being placed in an
   HttpOnly cookie;
4. Google Cast connections have no effective connect/read/write deadline and can consume blocking worker
   threads indefinitely.

The codebase still follows its no-direct-SQL application rule: no new `sqlx::query*` or raw domain SQL was
found under `backend/src`.

## Live Movies scan incident

### Evidence

- Library id `c64afe24-bbaf-4e29-ac2e-b5a85f413651` exists at `/data/media/Movies`.
- The path exists and contains eight supported movie files.
- The database contains eight `media_files` for that library, all unlinked; it contains zero movies for
  the library.
- The eight files represent four titles with duplicate root/organized copies, so duplicate cleanup will
  still be needed after matching.
- The active metadata setting contains no usable TMDB key.
- The current scan log repeats provider-search failures and zero-candidate warnings, then ends with
  `Library scan completed` at INFO.
- Six files have ffprobe data. Two Matroska files also have independent ffprobe JSON-analysis failures;
  those failures do not explain the zero-movie result because filename/provider matching can proceed
  without analysis.

### Root cause

The scanner correctly discovers and stores files first. It then tries local filename matching with
provider fallback disabled. Because the catalog has no existing `Movie` records, those files must fall
back to TMDB to create catalog entries. TMDB is unconfigured, so every fallback produces no candidate.
The provider helper previously converted those errors into `Ok(None)`, and batch processing returned no
summary to the main scan, allowing the final log to look successful.

### Remediation in this pass

- Preflight TMDB once before a movie fallback batch instead of issuing the same doomed request per file.
- Keep the discovered files unmatched; no file records or media bytes are removed.
- Create one unresolved, library-scoped `ACTION_REQUIRED` notification with a direct
  **Settings → Metadata** action. Repeated scans do not duplicate it while unresolved.
- Return provider matched/unmatched/error counts to the scan.
- Emit `Library scan completed with issues` at WARN when matching is blocked or incomplete.
- Preserve actual provider failures as errors when every search attempt fails.

After a TMDB API key is added, rescan the Movies library. The four duplicate title groups should then map
to four movie records with both physical copies linked; those duplicate physical files should be reviewed
before any deletion.

## Current risk register

### High — artwork URL fetch can reach internal services

`backend/src/services/artwork.rs` uses `reqwest::get(source_url)` with redirects and no client timeout,
scheme restriction, DNS/IP validation, or image MIME allowlist. The 20 MiB check occurs only after a
response is obtained. `recacheMovieArtwork` is member-accessible and fetches URLs from a movie row.
Because shared movie rows are member-writable under the default entity policy, a member can potentially
point artwork at loopback, link-local, or private-network resources and make the server fetch them.

Recommended fix:

- require admin for manual recache and restrict direct Movie URL mutation;
- use one configured client with connect/request/body deadlines and redirect limits;
- allow only HTTPS/HTTP, resolve DNS, and reject loopback, link-local, multicast, unspecified, and private
  destinations before every request and redirect;
- verify an allowed image content type and stream with a hard byte cap instead of buffering unboundedly.

### High — Cast sessions persist a real user bearer token without ownership

`castMedia` appends `RawAccessToken` to the stream query string, persists the complete URL as
`CastSession.stream_url`, and returns that URL through GraphQL. `CastSession` has no `user_id`, and the
row policy explicitly leaves it unscoped. A member who can read a shared session can therefore obtain
another user's still-valid access token and control/read shared cast-session state.

Recommended fix:

- mint a random, purpose-scoped cast grant bound to one media file, an expiry, and optionally a receiver
  address; store only a hash server-side;
- pass that grant in the receiver URL, not the user's API access token;
- never persist or return the secret-bearing URL;
- add `user_id`/ownership to sessions, or make sessions explicitly shared while keeping credentials in a
  separate non-GraphQL table;
- expire/revoke the grant on stop and cap its lifetime to expected playback duration.

### High — Cast network operations can block indefinitely

Cast operations use `spawn_blocking`, which protects the async runtime but not the blocking pool.
`rust_cast::connect_without_host_verification` uses blocking socket operations without an application
deadline. An unreachable or hostile stored address can leave connect/control calls and request handlers
blocked indefinitely. Wrapping only the `JoinHandle` in `tokio::time::timeout` would not stop the underlying
blocking operation.

Recommended fix:

- use or patch a Cast transport that accepts a preconfigured socket with connect/read/write timeouts;
- cap concurrent connect/control attempts per device and globally;
- add retry/backoff only for transient failures and surface device health/last error;
- validate manual device addresses and ports before any connection.

### High — refresh token is still exposed to JavaScript

Login, registration, and refresh set an HttpOnly refresh-token cookie but also return the full
`AuthTokens` object in `AuthPayload.tokens`. That preserves the XSS theft path the cookie is meant to
remove. Secure-cookie detection also trusts `X-Forwarded-Proto`; it should only trust forwarded headers
from configured proxies.

Recommended fix:

- return only the access token and access-token expiry in GraphQL;
- accept refresh/logout through the HttpOnly cookie, with a short compatibility migration if required by
  existing clients;
- derive secure transport from the actual connection unless the direct peer is a trusted proxy;
- add CSRF protection if cookie-authenticated mutations expand beyond refresh/logout.

### Medium — incomplete error handling still allows misleading outcomes

- Auto-organize discards organization failures after a successful scan match.
- The auto-organize safety check fails open: if the guard itself errors, organization proceeds.
- `ContentStatus::compute` remains a stub, leaving several advertised states unreachable.
- Several provider/artwork HTTP clients still use `Client::new()` or global `reqwest::get` without
  consistent timeouts.
- Two current Matroska files fail ffprobe JSON analysis but the visible scan completion did not aggregate
  analysis failures.

Recommended fix: make scan/analyze/organize outcomes first-class counters, fail the organization guard
closed, retain per-file remediation details, and use one deadline-configured HTTP client policy.

## Casting service assessment

### What is solid

- Blocking discovery and Cast protocol work is kept off the async runtime.
- mDNS now reuses one daemon and performs explicit shutdown.
- Discovery and control errors are propagated rather than presented as successful mutations.
- The scanner-to-cast MIME mismatch is fixed in this pass: generic stored values such as `video` and
  `audio` are no longer sent to a receiver as invalid MIME types; the file extension is used instead.
- Direct-stream casting remains intentionally separate from browser HLS policy, as documented by Q58.

### Hardening and functional gaps

1. **Validate all inputs.** Reject ports outside `1..=65535` before converting `i32` to `u16`; reject
   non-finite/negative seek and start positions; require finite volume in `0.0..=1.0`; validate addresses.
2. **Constrain connection targets.** Discovery results or admin-approved private/LAN addresses should be
   allowed. Arbitrary member-supplied hostnames/addresses make the service a network pivot.
3. **Separate protocols.** SSDP currently records a DLNA response's UDP source port and labels it a
   renderer, but playback still uses Google Cast V2. Fetch the SSDP `LOCATION` descriptor and implement
   UPnP AVTransport, or mark/hide DLNA devices as discovery-only.
4. **Make settings real.** Database `autoDiscoveryEnabled` and `discoveryIntervalSeconds` do not
   reconfigure the running service. `transcodeIncompatible` and `preferredQuality` are unused. Default
   volume is recorded in the session but is not sent to the receiver.
5. **Track the receiver session.** Every control command reconnects and selects the first running
   application/media session. Persist the receiver application/session identifiers and serialize commands
   per device to avoid controlling the wrong session.
6. **Synchronize status.** `playerState`, current time, and connection state are optimistic database
   values. Poll or subscribe to receiver status, expire disconnected sessions, and expose last-seen/error
   health.
7. **Improve discovery lifecycle.** Auto-discovery only updates an in-memory map; manual discovery persists
   devices. Stale entries are never evicted, `is_connected` is always false, and duplicates can race because
   address/port has no unique constraint.
8. **Use an explicit advertised media URL.** Selecting the first local IP can choose the wrong interface,
   and raw IPv6 hosts require brackets. Add a configured public/LAN base URL and verify it is reachable
   from the selected receiver.
9. **Add cast-specific compatibility policy.** Do not reuse browser capability assumptions, but do honor
   the casting transcode setting using receiver/device capabilities and a cast-specific direct/remux/
   transcode decision.

### Recommended casting delivery order

1. scoped stream grants + session ownership/no secret persistence;
2. target/input validation + real transport deadlines/concurrency limits;
3. receiver session/status tracking;
4. make persisted settings affect the live service;
5. explicit advertised URL and device capability policy;
6. implement DLNA AVTransport or remove the false playback promise.

## Earlier audit status

### Confirmed improved or implemented

- mandatory non-default JWT secret;
- fixed-origin CORS and authenticated media endpoints;
- configured bind host, SIGTERM, and graceful HTTP shutdown;
- production GraphQL introspection/playground controls and query limits;

- ownership row policy for playback progress/sessions and notifications;

### Still open or only partially addressed

- broad shared-entity authorization remains permissive for members;
- Cast sessions remain explicitly unowned;
- destructive startup schema changes still require careful operational gating/backup validation;
- `ContentStatus` remains incomplete;
- artwork serving remains unauthenticated by design, which may leak library images on a reachable host;
- scanner performance still includes blocking filesystem walking and many entity-layer round trips;
- auto-organize still discards errors/fails open in one path;
- Usenet, DLNA playback, AirPlay, subtitle acquisition/extraction, and Windows service integration remain
  incomplete or placeholders.

## Recommended project priority

1. Close artwork SSRF and cast token/session exposure before treating multi-user/LAN deployment as hardened.
2. Remove refresh tokens from response bodies and formalize trusted-proxy handling.
3. Add cast transport deadlines, target validation, and receiver status synchronization.
4. Finish scan/analyze/organize outcome aggregation and fail-safe organization behavior.
5. Complete authorization ownership rules for all user-private data and restrict raw generated mutations
   on shared/admin-managed entities.
6. Add dependency advisory/license checks to CI and keep focused integration tests for scan-with-missing-
   provider, cast grant expiry, artwork URL rejection, and multi-user isolation.
