## Highest-priority findings

1. **High: runtime torrent actions and streams bypass tenant ownership.** `services/graphql/entities/torrent.rs:391-438` authenticates a caller, then lists all live torrents, resolves arbitrary numeric IDs, or counts all active downloads. Live results include save paths and file paths (`:271-310`). `pauseTorrent` / `resumeTorrent` / `removeTorrent` authenticate but do not resolve an owned persisted Torrent before calling shared runtime operations (`:648-705`); removal accepts `deleteFiles`. Their info-hash variants at `:718-786` have the same boundary. The four custom subscriptions check only presence of `AuthUser`, subscribe to the shared runtime channel, and forward events without owner or role filtering (`subscriptions/torrents.rs:76,97,105,163,213,263`). Names, hashes, progress, and lifecycle information bypass generated subscription ACL. Fix all read/action/event surfaces together: resolve runtime IDs/hashes to persisted owned rows, reject unmapped rows for members, carry owner scope in trusted runtime envelopes, and preserve owner provenance on removal. Do not rely on frontend filtering or unauthenticated empty streams.
2. **High: public quality read/write resolvers use trusted repositories without owner scope.** `pendingUpgrades` calls `require_member`, builds only action/resolved/library predicates, and returns raw Notification entities (`queries/quality.rs:38-61`). No `user_id` filter or row policy is applied. Notification `actionData` can contain local source/target paths (`mutations/quality.rs:239-257`). `evaluateMediaFileQuality(mediaFileId)` similarly checks only member status (`mutations/quality.rs:92-95`), then `quality/profile.rs:801-827` reads and updates any supplied ID through the trusted repository. Require an authorized generated entity read before work; keep actor/owner through the action; persist through generated mutation or a narrow explicitly authorized transaction. `approveQualityUpgrade` is **admin guarded** (`mutations/quality.rs:194`); it is not the same unauthorized member-write finding.
3. **High: metadata action code promotes caller identity before verifying library ownership.** `addTvShow` accepts caller-supplied library ID and passes it straight to the provider service (`entities/show.rs:304-322`). That service constructs an admin AuthUser using the caller's ID (`metadata/providers.rs:2543-2547`) and then `Show::upsert(&self.db, ...)` (`:2596`) is a trusted write. The movie equivalent builds admin auth (`:2003-2007`) and calls `Movie::create_from_metadata` / `Self::insert(db,...)` (`:2049`; `entities/movie.rs:240`). These inspected chains contain no owner check on the target Library before privilege elevation. They can mix caller `user_id` with somebody else's library. Gate the target through the caller's generated Library read before provider fetching or internal promotion; inspect album/book refresh/add actions by the same rule. Cast does perform an explicit library-owner check (`entities/cast.rs:200-221`), showing an existing safe pattern.
4. **High for subscription-first migration: parent invalidation is partial, not absent everywhere.** Existing mutation hooks correctly create direct events for changed linked rows in one transaction (details below). They do **not** provide general child-to-Show/Album/Audiobook/Library invalidation, and metadata `notify_*_changed` helpers cover only selected provider flows. No entity declares the pinned `propagate_change="up"`. Removing polls based on the existence of `*Changed` roots will leave aggregates and relation-backed pages stale.
5. **High correctness/security: adopting propagation alone will still miss deleted children and old parents.** The pinned delete-propagation test explicitly expects no public parent event once the source child is deleted (`ORM/graphql-orm/tests/propagated_subscriptions.rs:854-923`). Update generation queues propagation from the **after** row (`operations.rs:8062-8089`); reparented old parents therefore have no automatically authorized current relationship. Use narrow generated parent revision mutations within the same authorized `MutationContext` where supported semantics cannot express the invalidation. Do not emit raw events or fake provenance.
6. **Medium: filesystem topic is wired but never emitted by current mutation implementation.** Broker is installed (`schema.rs:111`), subscription receives it (`subscriptions/filesystem.rs:68-79`), but real `createDirectory` succeeds without `.send()` (`mutations/filesystem.rs:339-358`). Delete/copy/move/rename are still `not_configured()` stubs (`:362-391`). The subscription's current check is any authenticated user, while filesystem mutation access is admin; make it admin scoped before activating it.

## Actual pinned write/event/cache behavior

### Generated repository writes are not raw SQL bypasses

`ORM/graphql-orm-macros/src/operations.rs:8391-8435` implements `Entity::insert(provider,input)` with two materially different branches:

- With **`&Database`**, it checks repository-surface policy, runs transforms/hooks, begins a `MutationContext`, writes, queues events, and commits/emits.
- With a **bare pool**, its fallback directly executes generated SQL and fetches the row; that fallback does not have the Database lifecycle/event context.

The 51 production writes below pass Database handles, not bare pools. Therefore they are **generated entity-layer, lifecycle-capable writes**, not 51 missing-subscription bugs. Under the requested strict GraphQL write convention they are still a separate set to migrate or narrowly allowlist. Repository access is explicitly trusted: `graphql/policy.rs:40-42`, `row_policy.rs:243-245`, and repository field policy `policy.rs:202-224` all return true. They do not apply the originating GraphQL caller's owner, role, or field checks. A manual resolver being authenticated does not make its subsequent repository operations scoped.

Generated typed helpers call before/after hooks and queue a typed changed event (`operations.rs:7932-7974`, `:8068-8089`, bulk `:8157-8218`). `MutationContext::commit_and_emit` commits the database first, emits all queued events second, and runs deferred actions third (`ORM/graphql-orm/src/graphql/orm/core.rs:1465-1492`). Rollback consumes the context without emitting (`:1495-1498`). App hook writes therefore share rollback/event ordering with their originating mutation. Deferred side effects fail via the registered error handler (`services/database.rs:97-98,842-853`); they cannot roll back a committed domain write.

Generated GraphQL mutations have additional request authorization/field selection/transform handling. The service helpers `library_scan.rs:637-661`, `metadata/providers.rs:456-486`, `torrent/database.rs:59-80` execute the shared schema and pass AuthUser + string user ID. Most helpers check top-level GraphQL errors; **business payload `success/error` must also be checked at each call site**. Some do (`library_scan.rs:1937-1949`, pending-match updates `:10870-10896`); metadata notification helpers discard the payload, so transport success does not prove the artificial update succeeded.

### Shared runtime, not EntityCache/EventBus objects

`db/mod.rs:1-2` aliases the upstream Database. The pinned Database owns `Arc<EventSenders>` and clones that Arc (`ORM/graphql-orm/src/db.rs:68-100`), so services and schema using clones share per-type channels. Each typed channel has capacity **256** (`db.rs:21,484-505`). A freshly constructed `Database::new(existing_pool)` would establish separate runtime state; do not construct a new wrapper for each job. Production database installation uses one service and shared clones (`services/database.rs:57-98`).

Generated relation DataLoaders use `Database.clone()` (`ORM/graphql-orm-macros/src/schema_roots.rs:455-473`; `ORM/graphql-orm/src/graphql/loaders.rs:937-966`). No application `EntityCache`, global entity cache invalidator, or EventBus bridge was found. Do not plan fixes against retired APIs with those names. `ArtworkCache` and `MetadataCache` are persisted domain entities; scanner candidate caches are separate in-memory ranking optimizations (`library_scan.rs:610-611`), not public GraphQL normalized caches. Apollo is a different client cache (`web/src/lib/apollo/client.ts:66-70`).

Generated public subscriptions consume a **`SubscriptionEvent<ChangedEvent,...>` witness**, not an arbitrary raw `ChangedEvent` (`operations.rs:7717-7718`). At delivery they validate keys, source provenance, current row, selected fields, and entity authority (`:7723-7763`). Repository-originated generated writes supply the authorized witness; a handcrafted `db.emit_event(FooChangedEvent)` would not substitute for it. This audit found no such raw application emission.

It is nevertheless an artificial extra row write, can replay a stale title over an intervening edit, bumps metadata, ignores payload failure, and does not cover arbitrary child changes. Replace the invalidation purpose with relation metadata where it fits; for non-relational artwork events use a narrow revision field/update or a specifically authorized topic. Do not add more same-value title/name writes.

### Safe use and limits of pinned propagation

Prefer `#[relation(target="Show",from="show_id",to="id",propagate_change="up",...)]` on Episode and the equivalent **child-side to-one** relationships above. Do not add propagation to parent `multiple` collections. The expansion uses `from` as a target primary key and calls `Target::__gom_fetch_by_id_on` (`ORM/graphql-orm-macros/src/operations.rs:1674-1714,2118-2144`); a non-PK `to` is not used to look up the parent. In particular, Movie.collection_id is a numeric TMDB provider ID, whereas local Collection.id is a string key; Collection.movies currently joins provider fields (`entities/collection.rs:91-97`). Introduce a local collection relation or a narrow authorized generated parent-revision lookup/update; simply annotating the existing reverse collection relation is wrong.

**Nullable multi-parent qualification hazard in this pin:** optional relation expansion uses `let Some(parent_id) = ... else { return Ok(()); }` (`operations.rs:2101-2105`). This returns from the whole propagation function, not merely the current edge block. If MediaFile is given optional Movie/Episode/Track/Chapter up relations, an absent first target can skip all later target edges. This is a concrete source-level risk in a proposed adoption; the app currently has no annotations, so it is not an existing application regression. Qualify nullable-edge order/multi-parent cases and obtain an upstream correction or use narrow per-target generated parent revisions; do not promise that simply annotating four optional relations provides complete fanout.

Pinned propagation deduplicates targets only within the traversal for one originating event, using source + target identity (`operations.rs:2133-2140`), and is bounded to **16 provenance hops / 256 targets** (`ORM/graphql-orm/src/graphql/subscriptions.rs:12-16`; `operations.rs:7821-7823`). Multiple child writes in one transaction still have separate traversals and can produce several parent invalidations. Metadata plus existing manual parent-touch helpers can duplicate invalidations. Set an explicit event cardinality contract: one direct event for each actual affected row, at most one invalidation per parent per logical operation/transaction if required, and client coalescing during large batches. Do not promise strict exactly-once network delivery.

**Deletion:** upstream test `propagated_subscriptions.rs:854-923` proves a deleted source cannot establish current provenance. Direct child delete has a trusted preimage; the app opts in (`row_policy.rs:270-289`), but derived ownership still reads the *current* parent. Deleting Library/Show/Album/Audiobook before delivery can therefore suppress corresponding child delete events for members. Parent deletion events and resnapshot must remove the whole stale subtree. For a surviving parent after child delete, perform a narrow generated `change_revision` update on that parent **inside the same transaction**; the public delivery then authorizes the current parent directly. This is a real parent write, not raw witness injection or a stale display-name touch.

**Reparenting:** propagation uses the updated row only (`operations.rs:8062-8089`); it reaches the new parent. Updating the old parent with provenance from a child that no longer belongs to it fails the current-relationship proof. Capture old and new parent IDs in the mutation preimage, authorize both parents against the actor before changing ownership, then update revisions for distinct surviving parents through `MutationContext`. Under bulk reparenting, collect distinct IDs across pre/postimages and apply one revision increment per parent in the shared transaction. A direct parent revision must preserve current parent ACL; never borrow a child user's authority for an unrelated parent.

`MutationContext` app hooks use the trusted repository surface, not inherited caller ACL (`operations.rs:8068-8069`; app `policy.rs:40-42`). The action/generated entry point must establish permission before reaching that branch. For a reusable ORM-level solution, use its operation authorization/typed context capabilities; do not claim the current generic context automatically carries request user enforcement. If a parent-revision API is missing, add it to the generated entity layer first. Keep child hooks for actual inverse-link persistence; add revision invalidation only where metadata cannot deliver the correct event. Review cascading delete ordering separately.

## Concrete transaction, deletion, delivery, and reconnect risks

- **Multi-request action workflows are not atomic.** Each generated mutation commits independently; schema execution does not turn several service requests into one transaction. Analyze clears stream groups then creates rows in a loop (`library_scan.rs:3961-4145`): mid-loop failure leaves a partially replaced stream graph and publishes intermediate events. Perform replacement plus revision in one transaction when adding the generated action layer. Same risk exists in source reordering (`entities/source.rs:870-872`) and register + invite consumption (`auth.rs:598-628`), while mark-all-read explicitly tolerates retryable partial success by product design.
- **Auth refresh rotation is a read/check/insert/update sequence, not atomic compare-and-swap.** `auth.rs:438-451` reads unrevoked preimage, inserts replacement, then updates old token in another transaction. No shared transaction or lock is in that implementation. Concurrent refresh requests could both pass the check, and a final update failure can leave an extra replacement. This is a static concurrency risk; existing sequential tests do not establish safety. Use the pinned ORM transaction + bounded conditional mutation/CAS capability (`ORM/graphql-orm/src/graphql/orm/core.rs:1572,1748`) with exact affected-row semantics for the old token and replacement in one transaction. Coordinate with the separate auth audit before changing in-flight prior work.
- **SQL cascades do not imply generated child hooks/events.** Episode->Show, Track->Album, Chapter->Audiobook, MovieCastCredit->Movie declare `on_delete="cascade"` (`episode.rs:126`, `track.rs:119`, `chapter.rs:94`, `movie_cast_credit.rs:63`). The app explicitly pre-deletes such rows for Library deletion, but no equivalent Show/Album/Audiobook/Movie before-delete hook is registered (`database.rs:1789-1829`). Direct generated parent deletion may let database cascade child rows without child events or inverse MediaFile cleanup. Add entity-layer transactional cleanup or a qualified dependency-invalidating parent deletion contract; test each direct and bulk root.
- **Not all scalar IDs have relational cleanup.** LibraryScanRun/Issue library IDs and VideoStream mediaFileId are plain fields, with no relation annotations (`library_scan_run.rs:32-34`, `library_scan_issue.rs:32-42`, `video_stream.rs:25-27`). Library cleanup omits scan-run/issue rows (`database.rs:911-1107`); MediaFile deletion hook only clears four media target links (`:1480-1497`). Decide intentional historical retention vs orphan cleanup, including stream/progress/session references, rather than relying on nonexistent FK cascades. No live database was inspected, so this is entity-source behavior, not a claim about legacy schema drift.
- **Bulk direct events can be filtered after the parent disappears.** The app delete-preimage policy explicitly requires the current parent for derived rows (`row_policy.rs:284-288`). During Library cascade, child deletes may have been queued correctly yet not delivered after commit. Always react to parent deletion by removing stale children or resnapshotting. Metadata up propagation alone cannot cure this.
- **Link hooks can produce multiple events for the same row.** Synchronization may update another representation of the same link in nested hooks (`database.rs:1403-1473,1500-1605`); setters prevent infinite recursion with equality checks, but normalization/wanted changes can still queue multiple actual updates. Exact-once means dedupe by logical operation/revision, not merely one function named notify.
- **Filesystem and database rollback remain distinct.** Organize moves first, persists path second, and explicitly attempts no-clobber compensation on failure (`library_scan.rs:8428,8482,8519-8557`); duplicate trash similarly restores on mutation failure (`:2754-2787`). Preserve this existing compensation. Quality approval replaces bytes then queues analysis and resolves notification separately (`mutations/quality.rs:259-281`); a failed/ignored queue can leave disk change with stale metadata. Add a durable action/progress record and retry/compensation contract where needed.
- **Delivery is bounded, lossy, and process-local.** ORM channel capacity is 256; generated stream calls `result.ok()?` on lag errors (`operations.rs:7723`), custom torrent streams do the same (`subscriptions/torrents.rs:105`). No replay cursor/sequence acknowledgement in these roots was found. The torrent backend itself logs lag and has a recovery sweep (`torrent/service.rs:1201-1207,1372`), but UI subscriptions lack equivalent catch-up guarantees. Add a revision/sequence and resnapshot after reconnect/lag, or explicitly use invalidation + network snapshot rather than pretending events are a durable journal.
- **Reconnect currently reconnects transport, not necessarily data.** `web/src/lib/apollo/client.ts:27-34` retries indefinitely; no connection-ready resnapshot callback appears there. Session changes terminate the socket (`:76-79`), but already mounted queries require invalidation/refetch after reconnect and principal changes. Keep initial query + subscribe race bounded with subscribe-before-snapshot or snapshot revision plus catch-up. Poll removal depends on this.
- **Runtime subscriptions and persisted state have different freshness.** Torrent DB sync runs every 10 seconds (`torrent/service.rs:1127-1155`); progress can arrive earlier from runtime stream. `web/src/features/downloads/useLiveTorrents.ts:22-48` still polls live state every 15 seconds, subscribes four runtime topics, and refetches persisted records only on add/complete/remove. Later postProcessStatus/error or linkage changes need generated torrentChanged invalidation too.

This is a **proposal**, not an authorization to weaken AGENTS or preserve arbitrary repository writes. Keep action roots where they express real work.
