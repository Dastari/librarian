## Findings and order of work

### Q1 — P1: generated Torrent subscription is shadowed out of the merged schema

`backend/src/services/graphql/schema.rs:13` glob-imports entity exports (including macro-generated `TorrentSubscriptions`), then `:22` explicitly imports the hand-written `subscriptions::TorrentSubscriptions`. Rust's explicit import wins. `schema_roots!` constructs every entity subscription identifier as `<Entity>Subscriptions` at `M/schema_roots.rs:263`; it does not qualify these names to their entity modules. Consequently the Torrent generated slot resolves to the custom type, which is also listed in `extra_subscription_types` at `schema.rs:78`.

The source explanation matches the SDL: `web/schema.graphql:11886` contains `torrentProgress`, `torrentAdded`, `torrentCompleted`, `torrentRemoved`; after `chapterChanged` the schema goes directly to `torrentFileChanged` (`:12041`). There is no `torrentChanged` or `TorrentChangedEvent`. `backend/src/services/graphql/subscriptions/mod.rs:7` re-exports the custom type. The document generator intentionally emits a Changed subscription only if the field exists (`web/scripts/generate-entity-documents.mjs:238`); therefore `web/src/graphql/entities/torrent.graphql` silently lacks a generated Changed operation.

Plan: alias the import as `TorrentClientSubscriptions` (or rename the hand-written type), use that distinct identifier in `extra_subscription_types`, and leave `TorrentSubscriptions` resolving to the entity-generated export. Assert that the exported schema has **46 entity Changed roots and five custom roots** (51 unique fields) and that both generated Torrent invalidations and runtime progress remain available. Regenerate schema/documents. This is a source-level name-resolution finding, not an unverified assumption that macro generation failed.

### Q2 — P1: `pendingUpgrades` is an unscoped notification list; generated replacement already exists

`backend/src/services/graphql/queries/quality.rs:38` calls `ctx.require_member()`, then at `:45` creates a filter on action type and unresolved state, optionally library at `:54`; at `:57` it calls `Notification::query(db.pool()).filter(filter).fetch_all()`. No requester/owner constraint is added. The action constant is `quality_upgrade` (`mutations/quality.rs:29`). Returning `Notification` does not automatically invoke generated root authorization.

Bypass verified in the pinned ORM, including the projection question:

- `M/operations.rs:8476` defines this pool-taking `query` as **FindQuery**, not the Database-taking RepositoryQuery. `R/graphql/orm/query.rs:4420` stores only a raw pool; `:4470` fetches through `PoolRef`.
- `R/graphql/orm/query.rs:3728` fetches/decodes rows without a GraphQL context, entity authorization, or row authorization. This path cannot recover the requesting `AuthUser` from `db.pool()`.
- Public generated roots instead call `ensure_entity_access(Some(ctx), ... GraphqlQuery)` and `read_visibility` (`M/operations.rs:7060`, `:7087`), then the authorized scanner checks rows. `OwnershipRowPolicy::decide` treats contextless/repository reads as trusted (`backend/src/services/graphql/row_policy.rs:236`); it classifies Notification as directly owned (`:98`). `AppEntityPolicy` does the same repository bypass (`policy.rs:39`).
- Notification's generated scalar getters have no row guard. In the macro, getter policy checks occur only for a declared **read** field policy (`M/entity.rs:4492`); Notification fields have owner/link **write** policies, not row-read checks (`entities/notification.rs:24`, `:46`, `:55`). `policy.rs:143` only checks field role for read policies; it does not restore notification ownership. Notification is not a protective projection DTO.

Thus any admitted member can receive another member's matching notification, including message/action data/IDs, if present. This is a static authorization proof; no runtime disclosure was attempted. It also fetches an unbounded set: `FindQuery::fetch_all` does not apply a default limit when no page is supplied (`R/graphql/orm/query.rs:3735`, `:1007`).

Replace the root and its caller `web/src/graphql/documents/activity.graphql:2` with:

```graphql
query PendingQualityUpgrades($where: NotificationWhereInput, $page: PageInput) {
  notifications(
    where: $where
    orderBy: [{createdAt: DESC}]
    page: $page
  ) {
    edges { node { id userId libraryId actionType actionData resolvedAt } }
    pageInfo { hasNextPage totalCount }
  }
}
```

Variables: `where = {actionType:{eq:"quality_upgrade"},resolvedAt:{isNull:true},libraryId?:{eq:libraryId}}`; include a current-user filter if the product wants administrators to see only their own feed too. The generated owner boundary must remain server-controlled; a client `userId` filter is not authorization. Page to completion for a complete client-filtered collection, or preserve an incremental server dataset with server filters. Use `notificationChanged` invalidations. Keeping the old wrapper briefly is possible only if it executes the generated/context-aware query or explicitly enforces owner policy; no new raw SQL is justified.

### Q3 — P1: `movieCollectionDetails` elevates a member and performs domain writes during a Query

Entry is authenticated but has no library ownership check: `entities/movie.rs:414`, `:426`, `:442`. It calls `MetadataService::get_movie_collection_details` with a caller-supplied library ID and requester ID. The service creates `AuthUser { role: Some("admin"), user_id: requester_id }` at `backend/src/services/metadata/providers.rs:2244`. It queries **all movies in that library**, in 500-row requests, using this identity (`:2252`, `:2281`). `execute_query` injects that identity into the GraphQL request (`:456`). `OwnershipRowPolicy::decide` returns true for admins (`row_policy.rs:249`), so generated roots do not compensate for that elevation.

The service then heuristically matches external collection parts and persists `tmdbId`, `collectionId`, name and poster changes using generated mutations at `providers.rs:2459`. The use of generated mutations is correct for event/validation plumbing but the identity and Query side effect are not. Depending on data/configuration, another library's local filenames/quality/linkage may be returned and movie metadata may be changed. Artwork caching is also performed (`:2232`), which is distinct from those domain writes.

Plan: retain an external collection-details read, but pass the **actual caller's authorization context**, require visible `library(id)`, and read `movies(where:{libraryId:{eq:L}, collectionId:{eq:C}},...) { node { ... mediaFile {...} } }` for the existing-membership overlay. If heuristic matching against unlinked local movies is required, fetch authorized library candidates and clearly distinguish suggested matches. Move persistence to an explicit authorized action mutation, preferably an existing add/refresh collection path. Keep provider-only DTOs for external items absent from the DB; represent an existing local match with a `Movie` relation rather than flattening a second Movie schema. Never manufacture admin authority to simplify reads.

### Q4 — P1: live Torrent queries expose global runtime state to every authenticated account

`entities/torrent.rs:391`, `:407`, `:427` merely obtain an `AuthUser` and discard it. `TorrentService::list_torrents` enumerates the entire librqbit session (`services/torrent/service.rs:333`); `get_torrent_info` takes an unchecked numeric runtime ID (`:370`); `list_active_downloads` filters only states (`:356`). These service APIs accept no user identity. `service_torrent_to_live` (`entities/torrent.rs:288`) returns names, files, linkage, and source information. This is independent of generated Torrent row policy.

Retain runtime reads, but first query the generated/authorized persisted `torrents` by requester and map their **infoHash** to the runtime session. For `liveTorrent(id)`, resolve the runtime record and require a visible persisted Torrent with the same hash before returning it. Global counts may remain admin-only; member counts must count only visible torrents. Do not replace current runtime progress with a persisted-state aggregate and assume equivalence. The four custom Torrent subscriptions have a parallel account-scoping issue (`subscriptions/torrents.rs:77` only checks AuthUser presence); the write/event audit should own stream-path remediation.

### Q5 — P1 correctness: Collection.movies omits the library half of its key

`entities/collection.rs:91` joins `Collection.tmdb_collection_id → Movie.collection_id`, with no `library_id` constraint. A member may own two libraries containing the same TMDB collection. Both sets pass row ownership checks, so this relation returns movies/counts from both libraries; admin override can widen it further. Row authorization does not express parent-child membership.

Use a composite generated relation:

```rust
#[relation(
    target = "Movie",
    from = ["library_id", "tmdb_collection_id"],
    to = ["library_id", "collection_id"],
    multiple,
    emit_fk = false
)]
```

Pinned parsing supports arrays at `M/entity.rs:2296`; generated key loaders construct composite keys (`M/relations.rs:615`); installed examples use composite arrays and `emit_fk=false` (`ORM/crates/graphql-orm/tests/composite_relations.rs:97`). `emit_fk=false` is deliberate: this is an inverse collection relation against nullable/non-unique movie metadata, not a physical FK from collections into movies. Multiple relations already default to not emitting an FK (`M/entity.rs:3512`), but explicit false documents intent. Add a `(library_id, collection_id)` lookup index if measured query plans warrant it; audit existing duplicates before introducing uniqueness for `(library_id,tmdb_collection_id)` on Collection. No uniqueness or migration was applied in this audit.

`Movie` has **no existing collection relation**; only `library` and `mediaFile` exist at `movie.rs:195`, `:204`. A proposed `Movie.collection` would require the reverse composite key, nullable source handling, `emit_fk=false`, and duplicate/absent Collection semantics. Do not mark that relation as already usable or turn on `propagate_change="up"` for a non-PK collection ID: current propagation fetches the target by **primary key**, not by the general relation mapping (`M/operations.rs:2117`). To propagate from Movie to a Collection either store a stable Collection row ID or extend the ORM to propagate by validated composite relation keys.

### Q6 — P1 scalability prerequisite: callback-only ownership defeats batching and bounded-page efficiency

The application installs only `OwnershipRowPolicy` callbacks (`database.rs:91`, `row_policy.rs:279`); it does not override `RowPolicy::read_visibility`. The pinned default returns `ReadVisibility::CallbackOnly` (`R/graphql/orm/core.rs:2593`). Therefore:

- Generated connection roots enter `scan_authorized_query` even when the caller supplied an owner filter (`M/operations.rs:7087`). It scans the entire candidate dataset to produce the authorized total, not just one visible page (`R/graphql/loaders.rs:405`, `:431`). Authorization remains correct; the old comment in `row_policy.rs:5` about post-pagination correctness is no longer a complete description of pinned behavior.
- App scan bounds are batch size 256 and **100,000 candidate rows** (`database.rs:86`). Budget exhaustion fails closed, not a partial count. A valid first page over a larger dataset can therefore fail.
- Multiple relation batching is gated on `!visibility.requires_residual_checks()` (`M/relations.rs:798`). The current policy disables that loader fast path, even though `schema_roots!` registers loaders for every entity (`M/schema_roots.rs:455`). Singular traversal similarly performs target checks. Derived checks themselves load a Library/Show/Audiobook/Torrent/MediaFile per row (`row_policy.rs:114` onward), producing additional N+1 reads and potentially repeated two-hop ownership lookups.
- Schema depth 20 and complexity 10,000 (`schema.rs:116`) are useful admission bounds, not a database-row scan or statement-count budget. Increasing those limits or the scan ceiling does not solve the ownership-query issue.

Implement complete SQL-visible ownership predicates through the **ORM's existing `RowPolicy::read_visibility` contract**, with default deny and explicit admin behavior. Direct owner entities can use equality on `user_id`; derived entities need authorized parent membership expressed through supported typed query predicates or a reusable entity-layer extension, not application raw SQL. Prove SQL predicate and callback equivalence for all 46 scope entries. Keep callback fallback where a complete predicate cannot be proven. Add selective owner/library/parent indexes and one request-scoped ownership loader if needed. Only then claim that nested relation loading avoids N+1 in this application.

### Q7 — P2: local helper reads silently lose runtime pagination configuration; aggregates require authorization work

The app explicitly selects legacy **1000 default /1000 max** connection limits at `database.rs:90`. Raw-pool `FindQuery` uses `PoolProvider` defaults **50/100**, not the app Database's overrides (`R/graphql/orm/query.rs:1450`, `:4470`, `:931`). With no explicit limit, FindQuery fetches all rows; with `.limit(200)` or `.limit(500)`, its explicit limit is capped at 100. For example `showcaseArtwork` requests 200 but inspects at most 100 rows (`entities/schedule_cache.rs:125`); the returned maximum 24 remains bounded, but selection is neither exhaustive nor ordered. Avoid interpreting an early short page as proof of complete data when mixing these APIs.

`contentStatuses` deliberately caps input at 500 (`queries/content_status.rs:44`) and batches fact reads. Its `FindQuery` calls have no page limit and are **not** truncated to 50/100 merely because they are pool-based. Preserve that distinction. Explicitly document internal batch cardinality and paginate or deduplicate larger fan-outs; do not mechanically add `.limit(500)` to a raw-pool query and introduce a 100-row bug.

The ORM supports typed aggregate `group_by`, count rows/non-null field, min, max, exact sum, up to 16 grouping fields/32 metrics (`R/graphql/orm/query.rs:2244`). Public `<plural>Aggregate` is opt-in via `aggregate=true` (`M/operations.rs:6178`), absent from all 48 entity definitions. The current SQL aggregate executor rejects callback-only visibility (`R/graphql/orm/query.rs:2611`); adding an annotation alone will not make owner-safe aggregates work. AVG, arbitrary SQL aggregate expressions, arbitrary cross-entity group joins, HAVING, user-chosen metric sorting, and per-group top-one/row-number are not methods in the inspected typed grouped query surface. Do not promise them or introduce SQL outside the entity layer. Some values can be computed as count/sum ratios after a correctly scoped aggregate. Add ORM/entity-layer capability only for the remaining actual product query.

## Missing relations and parent/sibling invalidation map

`propagate_change="up"` is supported at the **relation declaration**, not inferred from `on_delete="cascade"`, inverse fields, or ordinary FK scalar names. `M/entity.rs:2664` defaults to none; `M/operations.rs:1666` selects only explicitly annotated relations; `:2117` fetches the target by primary key and queues a provenance-bearing related event. The old rule's `notify="libraries"` example is not the current mechanism: pinned `notify/notify_with` expects a **Rust handler path** (`M/operations.rs:1375`).

A pinned-ORM propagation hazard needs an explicit regression before adding several nullable parents: `M/operations.rs:2101` generates `let Some(parent_id) = entity.<optional_fk>.as_ref() else { return Ok(()); };` inside the propagation function. A null optional FK can return from the whole propagation function and skip later sibling relation blocks. With planned MediaFile target or PendingFileMatch target relations, a null `episode_id` must not suppress a later non-null `movie_id` parent. Fix this in the ORM/entity-layer generation or use an explicit correctly bounded change-impact hook; do not assume that adding annotations to all nullable targets is sufficient. The same propagation code uses primary-key fetches and does not reproduce general composite/conditional relation matching. This hazard is dormant with zero current annotations and is a prerequisite for the proposed graph, not a claim of a currently emitting broken parent path.

The intended direction is **child row → singular parent row**. Adding `propagate_change="up"` on `Library.shows` or `Show.episodes` (parent→multiple child) would use the parent's PK as if it were the target PK; do not do that. Existing upward candidates below use actual FK→target.id. Both endpoints of reparenting/unlinking, creation/deletion, authorization of related invalidations, and post-commit emission must be verified by the companion write/event audit. Declaration presence alone cannot prove any write path emits. Do not publish every playback tick up to an entire library when only progress consumers need it.

## Query shapes and capability boundaries for implementation

1. **Ordinary get/list stays generated.** Examples already available: `show(id){episodes(where:{season:{eq:2}},orderBy:{episode:ASC},page:{limit:100,offset:0}){edges{node{id mediaFile{id path}}} pageInfo{hasNextPage totalCount}}}`, `artist(id){albums(...){...}}`, `audiobook(id){chapters(...){...}}`. Root connections permit multiple sort inputs; nested connections currently accept one. Use a stable ID tie-breaker in keyset configuration or a reviewed entity default when equal sort values matter. Current offset connections are not stable snapshot cursors across inserts/deletes.
2. **Parent membership is not root authorization.** `Collection.movies` must include library; `library.mediaFiles(where)` must still constrain membership independently of target filters. For Episode root there is `showId` but no `libraryId`; obtain authorized Show IDs or add an entity-layer parent predicate. The current generated `EpisodeWhereInput` (`web/schema.graphql:3193`) and `ShowWhereInput` (`:11402`) expose scalar filters and and/or/not; they do not expose `show:{...}` or `episodes:{some:...}`. Do not invent Prisma-style nested existential filters because nested *selection* resolvers exist. Extend the entity layer if an actual screen needs them.
3. **Progress and counts:** generated child connections already return authorized totalCount, and filtered child connections can count linked files (`where:{mediaFileId:{isNull:false}}`). Doing two counted nested connections for each of 100 parents under callback visibility can be expensive (Q6). For downloaded/total per Show/Album/Audiobook, implement owner-safe grouped counts in the entity layer, or verified generated computed fields backed by a request batch. Preserve `contentStatuses` as authoritative status precedence, not a direct alias for `hasFile` or a stored status column.
4. **Existing stored summaries are not automatically computed.** `Movie.download_status/has_file` (`movie.rs:167`), Album.has_files/size_bytes (`album.rs:125`), Audiobook.has_files/size_bytes (`audiobook.rs:131`), Artist counts (`artist.rs:64`) and Collection.movie_count (`collection.rs:59`) are ordinary persisted fields in these declarations. No hand-written relation/computed resolver maintains them here. Audit write maintenance or replace their presentation with canonical query-time aggregates. `docs/design.md:1177` describes desired computed progress, not proof that such fields exist in the current SDL. Do not sort/filter on stale summary fields without defining maintenance semantics.
5. **Continue Watching latest-per-title is not a plain CRUD alias.** Current progress is keyed by user/mediaFile, not logical edition/title. Adding relations makes title traversal possible but does not supply partitioned latest-per-show/book/album. A first 1000 progress rows followed by client grouping is not dataset-exhaustive. A typed entity-layer top-per-group capability or a materialized per-user resume aggregate with correct events is needed; retain external/runtime custom read only if it implements that contract safely.
6. **Keyset exists but is not enabled.** Pinned `M/operations.rs:1539` validates a declared `keyset="field asc|desc,...,id asc|desc"` ending with the PK tie-breaker, with optional explicit null ordering. No current entity uses it, so no `<plural>Keyset`/`<plural>Scan` root exists. Opt in for chosen large lists only after ownership visibility is addressed; generated authorized scan continuations differ from offset paging and exact totals.
7. **Aggregate extension is constrained.** Typed aggregate supports count/min/max/sum and bounded group results. Generated public aggregate roots need `aggregate=true`; app callback visibility currently blocks them. Relation count **ordering** is supported by `order_aggregate(name="...",aggregate="count")` (`M/entity.rs:2334`), but does not itself add a count field, arbitrary aggregate function, or `where`-filtered nested statistic. Keep count metrics and ordering semantics separate.
8. **Subscription-first does not mean data arrives complete in events.** Existing generated documents select metadata only (`web/scripts/generate-entity-documents.mjs:251`). Use generated invalidations to coalesce authorized refetches of the current dataset, preserve previousData, handle removal/reparenting, and recover missed events on reconnect. A successful SDL codegen is not evidence of covered parent events; Q1 demonstrates a root can be missing without document validation failing.
